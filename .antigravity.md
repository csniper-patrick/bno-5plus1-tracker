# Antigravity Workspace Guidelines - BNO 5+1 Tracker

## Project Overview
**bno-5plus1-tracker** is an unofficial, 3rd-party Vue 3 web application designed for UK British National (Overseas) (BNO) visa holders to track, calculate, and manage their travel absence days, qualifications, continuous residence evidence, and address history on the "5+1" route toward Indefinite Leave to Remain (ILR / Settlement) and British Citizenship (Naturalisation).

*Note: This application is an independent 3rd-party tool provided for personal tracking purposes only. It is not affiliated with, endorsed by, or connected to the UK Home Office or UK Government.*

### Key Regulations & Application Data Tracked
1. **Full-Day Absence Rule**: Departure (start) and return (end) dates are partially spent in the UK and are excluded. Only complete 24-hour calendar days spent entirely abroad count as days absent.
2. **Rolling 12-Month Limit & 5-Year Sliding Window (ILR)**: Maximum **180 days** absent in any continuous rolling 365-day period during the 5-year qualifying period. If the 180-day rule cannot be satisfied within the baseline 5 years, the qualifying period automatically shifts/delays forward to the earliest subsequent compliant 5-year window, flagged with a yellow **"Delayed"** warning and active period peak scanning.
3. **5-Year Qualifying Period & Visa Expiry**: Calculated from BNO Visa Start Date or initial UK Arrival Date. Supports an optional **Visa Expiry Date** (defaults to 5 years after visa start), catering to 30-month initial visas or custom extensions, and displaying extension warning alerts if visa expiry precedes the earliest ILR settlement date.
4. **Auto UK Arrival Sync**: Automatic generation/updating of initial arrival absence record if UK Arrival Date > BNO Visa Start Date.
5. **Earliest ILR Application Date**: Applications can be submitted up to **28 days** prior to completing the 5-year continuous residence requirement.
6. **Naturalisation Chaining & Absence Limits**:
   - Baseline Naturalisation target date automatically inherits `ilrTargetDate + 1 year` when ILR is delayed (or uses explicit `ilrApprovedDate` when available).
   - Maximum **450 days** absent in the 5 years prior to naturalisation application.
   - Maximum **90 days** absent in the final 12 months prior to naturalisation application.
   - Physical Presence Requirement: Applicants must be physically present in the UK on the exact date 5 years prior to application. If the start date falls on an absent day, the start date automatically shifts to the earliest subsequent day present in the UK.
7. **Life in the UK & English Language (B1) Tests**: Status, test dates, test centers, unique reference numbers (URN), and qualification pathways.
8. **National Insurance Number (NI) Tracking**: Record NIN format in standard UK space-delimited layout (`QQ 12 34 56 A`), with automatic status promotion to "Received" upon entering an NI number.
9. **5-Year Continuous Residence Checklist**: Supporting evidence checklists (Council tax, P60s, bank statements, utilities) structured across Years 1 to 5.
10. **UK Address History Log**: Full residential address entries (Move-in/out dates, postcode, tenure type) required for Home Office SET(O) and Naturalisation AN applications.
11. **Document Vault & Binary Blob Persistence**: Drag-and-drop file storage (PDFs, scans, photos up to 10 MB), organized into category/year folders (`Year 1-5`, `Life in UK`, `English B1`, `Addresses`, `Other`), linked directly to continuous residence checklist items and address history, with direct new-tab browser file viewing (`window.open`) and IndexedDB blob persistence.
12. **User Guide & Operation Manual (`InstructionView.vue`)**: Step-by-step interactive manual with desktop/mobile screenshot toggle, detailed feature steps (Key Dates, Absences, Documents/NIN, Backups), and an extended FAQ section.
13. **Unified ZIP Backup & Flexible Import**: One-click export packaging structured data (`backup.yaml`), file manifest index (`files-manifest.yaml`), and binary document files in a folder hierarchy (`files/<folderId>/<filename>`). Import handles both `.zip` archives and standalone `.yaml` files.

- **Formatter & Test Runner**: Prettier 3 & Node.js native test runner (`node --test tests/tracker.test.js`)

### 1. High-Performance Absence Segment Tree ([segmentTree.js](src/utils/segmentTree.js))
To evaluate arbitrary date ranges efficiently over a 10-year period (up to 3,653 days):
- A **1-indexed Segment Tree** backed by a `TypedArray` (`Int32Array` of size `4 * N + 1`, 0th index unused) with standard binary child node formulas (`leftNode = 2 * node`, `rightNode = 2 * node + 1`).
- **Leaf Map & Fast Point Access**: Stores pre-calculated leaf node indices in `leafMap`. Provides $O(1)$ point queries via `queryPoint(idx)` utilizing `_getLeafNode(idx)` with bounds checking.
- **Sliding Window Optimization**: Enables $O(1)$ constant-time sliding window updates in `useAbsentsStore` (`max12MonthAbsenceInfo` & `naturalizationQualifyingPeriod`) by subtracting exiting days (`queryPoint(i - 1)`) and adding entering days (`queryPoint(i + 364)`).
- **Range Updates & Interval Building**: Range updates traverse leaves in $O(D \log N)$ time (where $D = \text{endIdx} - \text{startIdx} + 1$ is the range length in days) via `updateRange(qstart, qend, val)` and `build(intervals, val)`.
- **Range Queries**: $O(\log N)$ range sum queries for fast computation of absent days in any custom date interval or rolling window via `query(qstart, qend)`.
- **Leaf Coverage Array**: An `Int32Array` (`leafCover`) tracks trip coverage count per leaf index, ensuring leaf values in `tree` transition between `0` and `1` accurately when adding or deleting overlapping trips.

### 2. Centralized Date Utilities ([date.js](src/utils/date.js))
- **`parseDateUTC(input)` / `formatDateUTC(dateObj)` / `normalizeDate(val)`**: Prevents timezone offset shifts by strictly converting inputs to UTC midnight Date objects and validating year, month ($1\text{--}12$), and day ($1\text{--}31$) bounds to prevent JS `Date` overflow/rollover.
- **`calculateDays(startDateStr, endDateStr)`**: Full 24-hour day calculations excluding departure & return days.

### 3. IndexedDB Binary Blob Storage & Schema Migration ([dbService.js](src/services/dbService.js) & [fileStorageService.js](src/services/fileStorageService.js))
- **Schema Version 2**: `dbService.js` manages DB upgrades from v1 → v2, creating a dedicated `files` object store with `keyPath: 'id'` and an index on `folderId`.
- **Binary Blob Storage**: `fileStorageService.js` handles saving and loading raw file `ArrayBuffer` data, creating temporary Blob Object URLs for inline previews/downloads, updating metadata, and enforcing a 10 MB per-file limit.

### 4. ZIP & YAML Backup Services ([backupService.js](src/services/backupService.js) & [zipService.js](src/services/zipService.js))
- **ZIP Archiving**: `zipService.js` packages `backup.yaml` (full application state), `files-manifest.yaml` (file metadata index), and binary document files inside a `files/<folderId>/<filename>` folder hierarchy.
- **Flexible Import**: Auto-detects ZIP archives vs standalone YAML files, restoring absence logs, visa dates, qualifications, address history, and reconstructing document file blobs into IndexedDB.

### 5. Document & Qualification Store ([documents.js](src/stores/documents.js))
Manages non-absence settlement requirements and document vault metadata:
- **Storage Key**: `bno_tracker_documents_v1`
- **Data Sections**: `lifeInUk`, `englishTest`, `residenceChecklist` (Years 1-5), `addressHistory`, `uploadedFiles`, `folders`.
- **Address History & Sorting**: `sortAddresses` maintains chronological order by move-in date. `addAddress` returns the newly created record.
- **File Metadata Hydration**: Hydrates `uploadedFiles` metadata array from IndexedDB on startup without loading full binary blobs into memory until requested.

## Developer & Agent Guidelines

1. **Date Format & Handling**: Always work with standard `YYYY-MM-DD` strings for input dates. Use UTC dates (`parseDateUTC`) when indexing into the Segment Tree array to prevent timezone shifts.
2. **Segment Tree Synchronization**: When altering absence state in `useAbsentsStore`, ensure the segment tree is updated via helper functions (`addRecordToSegmentTree` / `removeRecordFromSegmentTree` / `rebuildSegmentTree`) to keep range queries accurate.
3. **UI & Action Menu Consistency**: Maintain Vuetify 3 component styling and use 3-dots vertical action menus (`v-menu` with `mdi-dots-vertical` activator and compact `v-list`) for table row actions across all views.
4. **Theme Support**: Ensure dark/light themes are respected using Vuetify's `useTheme()` hook and Union Jack palettes defined in `src/plugins/vuetify.js`.
5. **No Direct State Mutation outside Store**: Components should interact with data exclusively through store methods and computed properties.
6. **3rd-Party App Designation & Phrasing**: Maintain clear designation that this is an unofficial 3rd-party application. Avoid using "Home Office Compliant" or official certification wording; use "Rules-Aligned" or "Within Limit" terminology. Keep drawer navigation titles concise ("Absence", "Document") under the "Trackers" section.
7. **Automatic Documentation Maintenance**: Automatically review and update `README.md` and `.antigravity.md` whenever architectural changes, feature additions/modifications, or dependency changes occur during a task.

### 2. Page & Card Container Architecture
- **Max Width Container**: All primary view pages (`AbsenceView.vue`, `DocumentView.vue`, `ReferenceView.vue`, `InstructionView.vue`) must wrap their root layout in a centered container with `max-width: 1400px; margin: 0 auto;`.
- **Page Header Banner**: Standardized at the top of each view using `<v-card color="primary" class="mb-4 rounded-lg elevation-3" variant="elevated">` containing `<v-card-text class="pa-6 text-white">`, featuring an icon (`v-icon` size `x-large`), H1 title (`text-h4 font-weight-bold mb-1`), and subtitle (`text-subtitle-1 text-medium-emphasis`).
- **Standard Card Containers**: Use `<v-card class="rounded-lg elevation-2 bg-surface">` for content sections. Sub-cards, filter bars, and control panels use `elevation-1 pa-3 border` with `rounded-lg`.
- **Border Radius**: Always specify `rounded-lg` (8px border radius) on `v-card`, `v-alert`, `v-btn-toggle`, `v-chip`, and modal dialogs to maintain unified curved corners.

### 3. Layout Grid & Content Alignment
- **Top Alignment for Grid Columns**: In step-by-step tabs, feature cards, and multi-column grid layouts (`v-row`), always specify `<v-row align="start">` so text columns, lists, and action buttons gravitate to the top of cards rather than drifting to vertical center.
- **Flexbox Spacing Utilities**: Use Vuetify 3 gap utilities (`ga-2`, `ga-3`) combined with `d-flex align-center flex-wrap` for inline controls, headers, and chip groups. Avoid hardcoded inline CSS margins on flex child items.
- **Card Inner Padding**:
  - Primary Header Banners: `pa-6`
  - Main Section Cards: `pa-4`
  - Controls, Filter Bars & Sub-cards: `pa-3` or `pa-2`

### 4. Component Patterns & Typography Hierarchy
- **Section Titles**: Format card titles as `<v-card-title class="text-h6 font-weight-bold d-flex align-center ga-2">` paired with a leading `v-icon` (colored `primary` or context color).
- **Body & Captions**: Use `text-body-1` for primary paragraphs, `text-body-2` for list items and panel text, `text-subtitle-2 font-weight-bold` for section subheadings, and `text-caption text-medium-emphasis` for captions and timestamps.
- **Primary Buttons**: `<v-btn color="primary" variant="flat" prepend-icon="mdi-...">` with clear verb labels.
- **Secondary Buttons**: `<v-btn color="primary" variant="outlined">` or `<v-btn variant="tonal">`.
- **Table Row Action Menus**: Use 3-dots vertical action menus (`v-menu`) activated by `<v-btn icon="mdi-dots-vertical" variant="text" size="small">` with compact menu lists (`v-list density="compact"`).
- **Status Badges**: Use `<v-chip size="x-small" class="font-weight-bold" :color="...">` with explicit semantic status colors.

### 5. Media & Responsive Design Guidelines
- **Responsive Breakpoint Hooks**: Use Vuetify's `$vuetify.display.smAndDown` breakpoint hook for switching responsive layouts, drawer overlays, and mobile vs desktop viewport media.
- **Image Containers**: Wrap screenshot and preview images in `<v-img contain class="rounded border shadow-sm w-100">` with an explicit `maxHeight` property and a loading placeholder template (`<v-progress-circular indeterminate color="primary">`).
- **Dark/Light Theme Compatibility**: Never hardcode inline hex colors for text or backgrounds (e.g. `color: #000`). Use Vuetify theme color classes (`text-primary`, `bg-surface`, `text-medium-emphasis`) or CSS custom properties to ensure 100% theme compatibility.

## Antigravity Coding Rules

These rules apply to every task in this project unless explicitly overridden.
**Bias**: Caution over speed on non-trivial work. Use judgment on trivial tasks.

### Rule 1 — Think Before Coding
- State assumptions explicitly. If uncertain, ask rather than guess.
- Present multiple interpretations when ambiguity exists.
- Push back when a simpler approach exists.
- Stop when confused. Name what's unclear.

### Rule 2 — Simplicity First
- Minimum code that solves the problem. Nothing speculative.
- No features beyond what was asked. No abstractions for single-use code, scripts, or configurations.
- Test: would a senior engineer say this is overcomplicated? If yes, simplify.

### Rule 3 — Surgical Changes
- Touch only what you must. Clean up only your own mess.
- Don't "improve" adjacent code, playbooks, comments, or formatting.
- Don't refactor what isn't broken. Match existing style.

### Rule 4 — Goal-Driven Execution
- Define success criteria. Loop until verified.
- Don't follow steps blindly. Define success and iterate.
- Strong success criteria let you loop independently.

### Rule 5 — Leverage the model's strengths
- Use me for: large-scale context analysis, multi-modal data extraction, architectural drafting, and cross-file summarization.
- Do NOT use me for: deterministic transforms, executing pipelines, or tasks where simple scripts suffice.
- If a native tool or code can answer, let it.

### Rule 6 — Context is vast, but focus is critical
- While my context window is massive, do not unnecessarily bloat it with irrelevant logs or unrelated data dumps.
- If the project shifts to a completely new domain, summarize the current state and start fresh to maintain absolute precision.
- Surface any context drift. Do not silently lose track of the core objective.

### Rule 7 — Surface conflicts, don't average them
- If two patterns or configurations contradict, pick one (more recent / more tested).
- Explain why. Flag the other for cleanup.
- Don't blend conflicting architectures or patterns.

### Rule 8 — Read before you write
- Before adding code, read exports, immediate callers, shared utilities, and relevant deployment pipelines.
- "Looks orthogonal" is dangerous. If unsure why code or infrastructure is structured a certain way, ask.

### Rule 9 — Tests verify intent, not just behavior
- Tests (and CI checks) must encode WHY behavior matters, not just WHAT it does.
- A test that can't fail when business logic or system state changes is wrong.

### Rule 10 — Checkpoint after every significant step
- Summarize what was done, what's verified, what's left.
- Don't continue from a state you can't describe back.
- If you lose track of the state, stop and restate.

### Rule 11 — Match the project's conventions, even if you disagree
- Conformance > taste inside the repository.
- If you genuinely think a convention is harmful, surface it. Don't fork silently or introduce divergent setups.

### Rule 12 — Fail loud
- "Completed" is wrong if anything was skipped silently.
- "Pipelines pass" is wrong if any checks were bypassed.
- Default to surfacing system errors and uncertainty, not hiding them.
